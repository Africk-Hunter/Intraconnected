Firestore cost savings

Two things drove this app's Firestore bill: every edit also wrote and re-read a sync counter, and every change from another device re-read every idea. Both are now fixed in code, each with a fallback and a kill switch. A one-device user drops by about two thirds, a two-device user by about four fifths.

One device

A device that is provably alone skips the meta/sync write. Halves writes and removes the echo reads.

Two devices

A pull reads only ideas changed since the last one, not all of them.

Not tried yet

Typecheck and 345 tests pass. The two-browser test run is still to do.

Numbers are modelled from the code, not measured. Check them against the Firebase Console Usage tab after release.

How Firestore bills

  • Billing is per document: one read per document returned, one write per document created, updated or deleted.
  • A listener bills one read for its first result, then one read for every document change it receives, including changes this same device made.
  • Security-rule lookups (get(), exists()) and count() aggregations (1 read per 1000 entries) are billed as reads.
  • The free quota is 50k reads and 20k writes a day for the whole project.
  • Companies cut costs by fetching less (limits, count()), caching, replacing polling with listeners, using a small change-marker document, and merging writes. This app already does the last two.

What keeps it safe

Both changes only ever take a shortcut when they are certain. Anything else does exactly what the app did before.

SituationWhat happens
First pull on a device, new account, or no watermark yetFull pull, as before.
An idea was deleted on another deviceThe server's idea count no longer matches. Full pull.
Any changed idea fails to decryptFull pull.
Delete or Discard from the sync banner, or a change hit a deleted ideaFull pull.
More than 7 days since the last full pullFull pull. Also catches edits from a tab still on the old build.
Unsent edits on this device during a pullRe-applied on top of the result, exactly as in a full pull.
Offline, cached view, or the live listener stoppedEvery write bumps the counter, as before.
A second device appearsIt registers; this device sends one catch-up bump, so the new device pulls everything changed meanwhile.
Something looks wrong in productionFlip INCREMENTAL_PULL or SOLO_SKIP to false and deploy. Or set sync_force_full / sync_always_bump to "1" in one browser's localStorage.

No Firestore rules change and nothing to migrate. Existing ideas are not rewritten.

Estimated improvement

Assumed: one session a day, 30 edits (about 15 distinct ideas), 200 ideas, and for two devices 3 pulls a day with about 5 ideas changed on the other device each time. Quotas are project-wide: 50k reads and 20k writes a day. The echo read per edit follows Google's listener billing rules and should be confirmed in the Usage tab.
